## Waterfall Pricing — Complete Flow

### Step 1: Load product + compute floor (`lines 352-357`)

```
Input: productId, customerId
→ Fetch product from DB
→ Compute floor price: costPrice × (1 + minMarginPercent/100)
   e.g. $260 cost × 1.05 = $273 floor
```

If product is soft-deleted → early return with base price, empty waterfall.

### Step 2: Load customer + find their groups (`lines 378-392`)

```
→ Fetch customer with memberships
→ Extract all groupIds they belong to
→ Build a filter: [this customer, any of their groups, global (null/null)]
```

For example, MegaMart in VIP + Premium Partners + Chain Stores:
```
filter = [
  { customerId: "megamart-id" },           // customer-specific profiles
  { customerGroupId: { in: ["vip", "premium", "chain"] } },  // group profiles
  { customerId: null, customerGroupId: null }  // global profiles
]
```

### Step 3: Fetch all candidate profiles in parallel (`lines 394-422`)

Two queries run simultaneously:
- **Published profiles** — `status: 'published'` matching the filter
- **Draft profiles** — `status: 'draft'` matching the filter AND covering this product

Both queries include `profileProducts: { where: { productId } }` to pull the junction row for custom pricing.

### Step 4: Filter published profiles to those covering this product (`lines 424-427`)

```
matchingProfiles = publishedProfiles.filter(p =>
  p.scope === 'all' OR p.profileProducts.length > 0
)
```

A profile with `scope: 'all'` always matches. A `scope: 'selected'` profile only matches if its junction table has this product.

### Step 5: Build entries with computed prices + tiers (`lines 429-460`)

For each profile, `buildEntry()` does:

1. **Compute the price** this profile would produce:
   - `custom` → use `customPrice` from junction row (or base price if missing)
   - `fixed` → `basePrice ± adjustmentValue`
   - `dynamic` → `basePrice ± (basePrice × adjustmentValue / 100)`

2. **Compute the tier** (1-6) via `computeTier()`:
   ```
   Has customerId?     → selected=1, all=2
   Has customerGroupId? → selected=3, all=4
   Neither (global)?    → selected=5, all=6
   ```

### Step 6: No matches → early return (`lines 462-490`)

If zero published profiles match, return base price. Draft profiles still appear in the waterfall as `rejected` so the supplier sees what *would* apply.

### Step 7: Sort + pick winner (`lines 492-498`)

```
sort by: tier ASC first, then computedPrice ASC
winner = first entry after sort
```

This is the core decision: **lowest tier number wins** (most specific). Within same tier, **lowest price wins** (best deal for customer).

### Step 8: Apply floor protection (`lines 500-501`)

```
if floorPrice exists AND winner.computedPrice < floorPrice:
  finalPrice = floorPrice  (clamped UP)
else:
  finalPrice = winner.computedPrice
```

### Step 9: Build the waterfall array (`lines 503-571`)

Loop through all entries and assign verdicts:

**Published entries (in sorted order):**
- Winner → `verdict: 'won'`, reason includes floor note if clamped
- Same tier but higher price → `verdict: 'lost'`, reason: "Same tier (X) but higher price than 'Winner' ($Y > $Z)"
- Lower tier → `verdict: 'lost'`, reason: "Lower specificity tier (X vs winning tier Y)"

**Draft entries (appended at end):**
- All get `verdict: 'rejected'`, reason: "Profile is in draft status"

Each entry carries: position, profileName, tier, tierLabel, computedPrice, priceAfterFloor, verdict, reason.

### Step 10: Compute margin insight (`lines 573-574`)

```
sameTierEntries = all published entries at the winner's tier
if 2+ entries at same tier:
  avgPrice = average of their computedPrices
  divergence = (finalPrice - avgPrice) / avgPrice × 100
  if |divergence| > 10% → triggered=true with warning message
```

### Step 11: Return everything (`lines 582-597`)

The response includes: `finalPrice`, `appliedProfile`, `tier`, `tierLabel`, `reason`, `floorPrice`, `floorApplied`, `waterfall[]`, `marginInsight`.

## Why Waterfall is better than alternatives

### vs. "Just return the final price" (no waterfall)

Without a waterfall, the supplier sees "$250" but has no idea *why*. If the price seems wrong, they have to manually check every profile, every group membership, every product assignment. The waterfall gives them the complete audit trail in one response — every profile considered, who won, who lost, and exactly why.

### vs. "Last updated wins" (recency-based)

Recency is fragile. If someone edits an old global profile, it silently becomes the new winner for every customer. The waterfall's tier system makes the outcome **stable and predictable** — a customer-level deal always beats a group promo regardless of when either was created or last touched.

### vs. "Lowest price always wins" (flat comparison)

Without tiers, a global "2% off everything" promo could accidentally override a carefully negotiated customer-specific deal. The waterfall evaluates specificity first, price second. A supplier who negotiated $95 with Bondi Cellars knows that price is honoured — group promos appear in the waterfall as `lost` entries, not silent overrides.

### vs. "Black box" pricing engines

Many pricing systems give you a final number with no explanation. The waterfall is fully transparent — the `reason` field on every entry is a human-readable sentence explaining exactly what happened. This means:
- **Debugging** is instant: you see every candidate and why it won/lost
- **Customer disputes** are easy: show them the waterfall
- **Misconfigured profiles** surface naturally: the margin insight flags when the winning price diverges >10% from same-tier peers

### The floor + waterfall interaction

The floor doesn't just silently clamp — it shows up in the waterfall. The winning entry gets `priceAfterFloor: $273` and the reason says "floor applied ($250 → $273)". The supplier can see the profile wanted to charge $250 but the margin protection raised it. Without this visibility, they'd never know the floor was active.

Yes, they create a **floor price** — the minimum price a product can ever be sold at, regardless of what any pricing profile calculates.

## How it works

**Formula**: `floorPrice = costPrice × (1 + minMarginPercent / 100)`

Example: A wine costs $10 to buy (`costPrice = 10`) and you want at least 20% margin (`minMarginPercent = 20`):
- `floorPrice = 10 × (1 + 20/100) = 10 × 1.2 = $12.00`

## Where it kicks in

During price resolution (`resolveAllPrices`), after the waterfall picks a winning profile price:

1. Waterfall determines the winning price is **$11.00** (from some profile with a decrease)
2. Floor price is **$12.00**
3. Since `$11.00 < $12.00`, the floor is applied → final price becomes **$12.00**
4. The response marks `floorApplied: true` and the waterfall entry shows `priceAfterFloor: 12.00`

If the winning price was **$14.00**, the floor doesn't trigger — `floorApplied: false`, final price stays $14.00.

## What if they're null?

Both fields are optional. If either `costPrice` or `minMarginPercent` is null, no floor is calculated — the winning profile price is used as-is with no protection. This is handled in `computeFloorPrice()`:

```typescript
if (costPrice == null || minMarginPercent == null) return null;
```

## Why it matters

It prevents pricing profiles from accidentally selling products **below cost**. A supplier might set a 10% decrease for a customer group, but if that decrease would push the price below the profit margin, the floor catches it and protects the business.

Here are the key trade-offs in your project:

## 1. Soft Delete vs Hard Delete (Products)
**Chose**: Soft delete (`deletedAt` timestamp)
**Why**: Preserves historical data, allows recovery. Junction rows are cleaned up immediately but the product row stays.
**Trade-off**: Table grows over time, every product query needs `deletedAt: null` filter.

## 2. Live Query vs Stored Rows for `scope: 'all'`
**Chose**: Live query — no junction rows stored, queries all products with `deletedAt: null` at resolution time.
**Why**: New products automatically get pricing, deleted products automatically excluded. Zero maintenance.
**Trade-off**: Slightly slower resolution (full table scan each time) vs `scope: 'selected'` which uses pre-stored junction rows.

## 3. Specificity Tiers (6-tier) vs Simpler Approaches
**Chose**: Fixed 6-tier hierarchy (customer+selected > customer+all > group+selected > group+all > global+selected > global+all).
**Why**: Deterministic, predictable, easy to explain. Most specific always wins.
**Trade-off**: No priority override — you can't make a group profile beat a customer profile. Rigid by design.

## 4. Floor Price Protection vs Letting Profiles Decide
**Chose**: Hard floor at `costPrice × (1 + minMarginPercent / 100)`.
**Why**: Prevents selling below cost regardless of what profiles calculate.
**Trade-off**: A business user can't intentionally price below cost (e.g., loss-leader strategy) unless they remove the cost price / margin from the product.

## 5. First-Created Wins for Same-Tier Tiebreak
**Chose**: When two profiles share the same tier, the one created first (`createdAt ASC`) wins.
**Why**: Simple, stable, no extra "priority" field needed.
**Trade-off**: Users can't reorder priority without deleting and recreating profiles.

## 6. Draft vs Published Status
**Chose**: Only `published` profiles participate in price resolution. `draft` profiles are invisible to resolution.
**Why**: Lets users set up and preview before going live.
**Trade-off**: No scheduling — can't set a future publish date. It's immediate.

## 7. Waterfall Transparency vs Simple Response
**Chose**: Full waterfall array showing every profile evaluated with verdict (`won`/`lost`/`rejected`) and reason.
**Why**: Complete auditability — users see exactly why a price was chosen.
**Trade-off**: Larger response payload. For 50 products × 10 profiles = 500 waterfall entries per request.
