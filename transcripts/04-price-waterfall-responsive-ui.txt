# Price Waterfall — Salesforce-Style Resolution Response

## Context

The current resolver returns a flat response with a `candidateProfiles` array and a single `newPrice`. While functional, it doesn't tell the supplier **why** each profile won or lost — they have to mentally diff tier numbers and prices. Salesforce and other enterprise pricing tools use a **price waterfall** pattern: an ordered list of every pricing step that was evaluated, each with a verdict (won/lost/rejected) and the reason. This makes the pricing decision fully auditable at a glance.

**What changes:**
1. Replace `candidateProfiles` + `rejectedProfiles` with a single `waterfall` array — every profile that touched this product, ordered by evaluation priority, with win/loss verdict and reason
2. Add `marginInsight` — flags when the winning price diverges >10% from same-tier average (alerts suppliers to unexpected pricing gaps)
3. Keep all existing fields (`newPrice`, `appliedProfile`, `tier`, floor fields) for backward compatibility

**File:** `packages/backend/src/services/pricingProfile/index.ts`

Replace the current `candidatesWithTier` → sort → winner logic with:

1. Build `waterfallEntries` from all matching published profiles (same data as current candidates)
2. Also add draft profiles as `verdict: 'rejected'` entries
3. Sort: published entries by tier ASC then computedPrice ASC; rejected entries at the end
4. Assign `position` (1-based) to each entry
5. Pick winner (position 1 among published)
6. Apply floor to winner, set `priceAfterFloor` on the winner entry
7. Generate `verdict` and `reason` for each entry:
   - Winner: `"won"` — reason explains tier win + floor if applied
   - Same tier but higher price: `"lost"` — `"Same tier (X) but higher price than '{winner}' ($Y > $Z)"`
   - Lower tier: `"lost"` — `"Lower specificity tier (X vs winning tier Y)"`
   - Draft: `"rejected"` — `"Profile is in draft status"`

8. Compute `marginInsight`:
   - Collect all published entries at the same tier as winner
   - If ≥ 2 entries at same tier: calculate average price of those entries
   - `divergencePercent = ((winningPrice - avg) / avg) * 100`
   - `triggered = Math.abs(divergencePercent) > 10`
   - Generate message if triggered, null otherwise

## Old vs New: Comparison

### Old Approach — `candidateProfiles` + `rejectedProfiles`

| Aspect | Detail |
|--------|--------|
| **Structure** | Two separate arrays — candidates (published) and rejected (drafts) — with no verdict or reasoning per entry |
| **Winner logic** | Implicit — the first item in `candidateProfiles` happens to be the winner, but nothing in the data says so |
| **Why a profile lost** | Not available — the consumer has to mentally diff tiers and prices to figure it out |
| **Draft visibility** | Only shows name + "Profile is in draft status" — no computed price or tier info |
| **Floor insight** | Only on the top-level response, not per-entry |
| **Margin alerting** | None |
| **Frontend work** | Two separate sections to render, no unified view |

### New Approach — `waterfall` + `marginInsight`

| Aspect | Detail |
|--------|--------|
| **Structure** | Single ordered array — every profile in one place, sorted by evaluation priority |
| **Winner logic** | Explicit — `verdict: "won"` on exactly one entry |
| **Why a profile lost** | Every entry has a `reason` string: "Same tier but higher price", "Lower specificity tier", "Draft status" |
| **Draft visibility** | Full entry with computed price, tier, adjustment — same shape as published entries |
| **Floor insight** | Winner entry carries `priceAfterFloor`, making the floor clamping visible at the entry level |
| **Margin alerting** | `marginInsight` flags >10% divergence from same-tier average — proactive supplier alert |
| **Frontend work** | One table renders everything; color-coded badges make status scannable |

---

## Verdict: The waterfall approach is better

**Three key reasons:**

1. **Auditability** — Each entry is self-documenting. A supplier (or support engineer) can look at the response and immediately understand *why* a specific profile won or lost without comparing fields across entries. This is the core pattern used by Salesforce CPQ, Oracle Pricing, and similar enterprise tools.

2. **Single source of truth** — Two separate arrays (`candidateProfiles` / `rejectedProfiles`) force every consumer (frontend, reporting, integrations) to merge and correlate them. The waterfall eliminates that — one array, one sort order, one rendering loop.

3. **Proactive alerting** — `marginInsight` adds value the old approach simply didn't have. Flagging when the winning price diverges significantly from peers catches misconfigured profiles before they impact revenue.

**The only trade-off** is slightly more computation on the backend (generating reason strings, computing margin averages), but this is negligible compared to the DB queries already being made.
